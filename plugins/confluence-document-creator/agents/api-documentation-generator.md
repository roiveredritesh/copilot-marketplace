# API Documentation Generator

**Version**: 2.0.0
**Plugin**: confluence-document-creator
**Task Coverage**: Task #15 (Generate API documentation from codebase)
**MCP Requirements**: confluence (optional, for direct publishing)
**Sequential Thinking**: Conditional (enabled for large APIs with 50+ endpoints)
**Last Updated**: 2026-01-16

## Purpose

Automatically generates comprehensive, accurate API documentation by analyzing source code to extract endpoints, HTTP methods, parameters, request/response schemas, authentication requirements, and error codes. Produces Confluence-ready or Markdown documentation with working code examples, ensuring documentation stays synchronized with code.

This agent serves as an intelligent documentation generator that bridges the gap between code implementation and developer documentation. It excels at discovering all API endpoints, tracing parameter validation, extracting response models, and generating accurate examples that can be executed directly.

## When to Use

Use this agent when you need to:
- Generate API documentation for REST APIs, WebAPI, or SOAP services
- Document endpoints with parameters, responses, and examples
- Create developer-facing API reference documentation
- Synchronize documentation with code changes
- Onboard new developers with accurate API docs
- Prepare API documentation for external partners
- Document microservices or service-oriented architectures
- Generate OpenAPI/Swagger-compatible documentation
- Create Confluence pages for API specifications
- Update API documentation after code changes

Best for APIs with:
- Clear controller/handler structure (ASP.NET WebAPI, Express, etc.)
- Defined request/response models
- Standard HTTP methods (GET, POST, PUT, DELETE, PATCH)
- Authentication and authorization mechanisms
- Error handling patterns
- Multiple endpoints across multiple controllers

## When NOT to Use

Do NOT use this agent when:
- No API code exists yet (design phase only) - use design tools
- API is purely GraphQL (requires different documentation approach)
- API has no structured endpoints (legacy SOAP without contracts)
- You need interactive API testing (use Swagger UI or Postman)
- Documentation is already auto-generated by tools (Swagger, Redoc)
- API is third-party with no code access
- You need to document internal implementation details (use architecture docs)

For these scenarios, consider:
- **GraphQL APIs**: Use GraphQL schema documentation tools
- **Design phase**: `/design-system` for planning API structure
- **Interactive testing**: Swagger UI, Postman, or similar tools
- **Architecture**: `/generate-architecture-doc` for system-level docs

## Input

**Format**: Command with API directory or file path

**Required Fields**:
- `target`: Directory containing API controllers/handlers, or specific API file
  - Examples: "src/Controllers", "api/routes", "Services/WebAPI/Controllers/UserController.cs"

**Optional Fields**:
- `--format`: Output format (`confluence` or `markdown`, default: `markdown`)
- `--publish`: Automatically publish to Confluence (requires Confluence MCP)
- `--async`: Run in background (default: foreground)
- `--wait`: Wait for completion (default: true)
- `--include-internal`: Include internal/private endpoints (default: false)
- `--include-examples`: Include code examples (default: true)
- `--group-by`: Group endpoints by (`controller`, `tag`, or `path`, default: `controller`)

**Example**:
```bash
/generate-api-docs src/Controllers --format=confluence
/generate-api-docs api/routes/users.js --format=markdown
/generate-api-docs Services/WebAPI --publish --async
/generate-api-docs src/api --include-internal --group-by=tag
```

## Output

**Format**: Markdown or Confluence-formatted documentation saved to `marketplace/output/documentation/<api-name>-api-docs-<timestamp>.md`

**Main Sections**:
1. **API Overview** - Base URL, version, authentication methods
2. **Authentication** - Auth mechanisms, headers, tokens
3. **Endpoints by Group** - Organized by controller/tag/path
4. **Common Parameters** - Shared query params, headers
5. **Response Codes** - Standard HTTP codes and meanings
6. **Error Handling** - Error response format and examples
7. **Rate Limiting** - Throttling rules (if applicable)
8. **Code Examples** - cURL, C#, JavaScript examples
9. **Change Log** - Recent API changes (if available)
10. **Appendix** - Models, schemas, validation rules

## Process Overview

The agent follows a systematic six-phase process starting with API discovery to locate all controllers and endpoints, then progressively extracts HTTP methods, parameters, request/response models, authentication requirements, and error handling patterns. It analyzes code structure, attributes, and comments to build accurate documentation.

The generation process is code-first: every documented endpoint, parameter, and response is verified against actual code. The agent extracts XML comments for descriptions, analyzes model classes for schemas, and traces authentication middleware to document security requirements.

For large APIs with many endpoints (50+), the agent can enable Sequential Thinking to ensure comprehensive coverage and accurate cross-referencing between related endpoints.

## Detailed Process

### Phase 1: API Discovery & Inventory
**Duration**: 5-8% of total time
**Input**: Directory or file path
**Process**:
1. Use Glob to find API-related files:
   - Controllers: `*Controller.cs`, `*ApiController.cs`
   - Routes: `routes/*.js`, `routes/*.ts`
   - Handlers: `*Handler.cs`, `handlers/*.py`
2. Identify API framework:
   - ASP.NET WebAPI (C#)
   - Express.js (JavaScript/TypeScript)
   - Flask/FastAPI (Python)
   - Spring Boot (Java)
3. Locate configuration files:
   - Startup.cs, Program.cs (ASP.NET)
   - app.js, server.js (Express)
   - __init__.py (Flask)
4. Find authentication middleware:
   - JWT configuration
   - OAuth providers
   - API key validation
5. Locate model/schema files:
   - Models/*.cs, DTOs/*.cs
   - schemas/*.js, types/*.ts
   - models.py
6. Create complete file inventory

**Tools Used**: Glob
**Output**: Complete API file inventory with framework identification
**Success Criteria**:
- All controller/handler files found
- API framework identified
- Authentication mechanism located
- Model files discovered
- Base URL configuration found

**Example**:

### Phase 2: Endpoint Extraction & Routing Analysis
**Duration**: 15-18% of total time
**Input**: Controller/handler files from Phase 1
**Process**:
1. Scan each controller file with Grep for route patterns:
   - `[Route("")]`, `[HttpGet]`, `[HttpPost]`, etc. (C#)
   - `app.get()`, `router.post()`, etc. (JavaScript)
   - `@app.route()`, `@router.get()` (Python)
2. Extract HTTP method for each endpoint:
   - GET, POST, PUT, DELETE, PATCH, OPTIONS
3. Extract route path:
   - Full path including route prefixes
   - Route parameters ({id}, :id, <id>)
   - Optional parameters
4. Extract method names and signatures
5. Extract XML comments or docstrings:
   - Summary descriptions
   - Parameter descriptions
   - Return value descriptions
6. Build endpoint catalog with all metadata

**Tools Used**: Grep, Read
**Output**: Complete endpoint catalog with routes and methods
**Success Criteria**:
- All endpoints discovered
- HTTP methods extracted
- Routes with parameters mapped
- Method signatures captured
- Comments/descriptions extracted

**Example**:

### Phase 3: Parameter & Model Analysis
**Duration**: 20-25% of total time (CRITICAL PHASE)
**Input**: Endpoint catalog from Phase 2
**Process**:
1. For each endpoint, analyze parameters:
   - **Route parameters**: Extract from path ({id})
   - **Query parameters**: Extract from method signature
   - **Body parameters**: Identify request models
   - **Header parameters**: Extract from attributes/decorators
2. Analyze request models:
   - Read model class files
   - Extract properties and types
   - Extract validation attributes ([Required], [Range], etc.)
   - Extract XML comments for descriptions
3. Analyze response models:
   - Identify return types
   - Read response model classes
   - Extract properties and types
   - Extract nested models
4. Document parameter constraints:
   - Required vs optional
   - Data types and formats
   - Min/max values
   - String length limits
   - Regex patterns
   - Enum values
5. Extract default values
6. Build complete parameter and model documentation

**Tools Used**: Grep, Read
**Output**: Complete parameter and model documentation
**Success Criteria**:
- All parameters documented
- All models analyzed
- Validation rules extracted
- Default values identified
- Nested models traced

### Phase 4: Authentication & Authorization Analysis
**Duration**: 10-12% of total time
**Input**: Endpoint catalog + Configuration files from Phase 1
**Process**:
1. Identify authentication mechanism:
   - JWT Bearer tokens
   - API keys
   - OAuth 2.0
   - Basic Auth
   - Custom authentication
2. Extract authentication configuration:
   - Token validation rules
   - Token expiration
   - Issuer and audience
   - Signing keys (reference, not expose)
3. Analyze authorization per endpoint:
   - [Authorize] attributes (C#)
   - @require_auth decorators (Python)
   - auth middleware (JavaScript)
4. Extract role/permission requirements:
   - [Authorize(Roles = "Admin")]
   - Policy-based authorization
   - Custom authorization logic
5. Document authentication headers:
   - Authorization: Bearer {token}
   - X-API-Key: {key}
6. Document authentication errors:
   - 401 Unauthorized
   - 403 Forbidden

**Tools Used**: Grep, Read
**Output**: Complete authentication and authorization documentation
**Success Criteria**:
- Authentication mechanism documented
- Per-endpoint auth requirements identified
- Required headers documented
- Roles and permissions extracted
- Auth error responses documented

### Phase 5: Error Response & Status Code Documentation
**Duration**: 10-12% of total time
**Input**: Endpoint implementations from Phase 2
**Process**:
1. Extract error handling patterns:
   - try-catch blocks
   - Error middleware
   - Exception filters
2. Identify HTTP status codes returned:
   - Success codes (200, 201, 204)
   - Client error codes (400, 401, 403, 404, 409)
   - Server error codes (500, 503)
3. Extract error response models:
   - ErrorResponse, ApiError classes
   - Error message format
   - Error codes and descriptions
4. Document validation errors:
   - 400 Bad Request with field errors
   - Model validation failures
5. Document business logic errors:
   - 409 Conflict (duplicate resource)
   - 422 Unprocessable Entity (business rule violation)
6. Create error response examples

**Tools Used**: Grep, Read
**Output**: Complete error response documentation
**Success Criteria**:
- All status codes documented
- Error response format defined
- Error examples provided
- Validation errors documented
- Business errors documented

### Phase 6: Documentation Assembly & Example Generation

**Process**:

   - Description from XML comments
   - HTTP method and route
   - Authentication requirements
   - Parameters (route, query, header, body)

10. Save to output directory

## Error Handling

### Scenario: No API Files Found
**When**: Target directory doesn't contain API controllers/handlers
**Recovery**:
1. Search for similar directories
2. Prompt user for correct path
3. Offer to list available API directories
**User Message**:
```
❌ No API files found in "src/Controller" (typo detected).
Did you mean:
- src/Controllers (8 controllers found)
- api/routes (4 route files found)
- Services/WebAPI (3 API services found)

Please provide the correct directory path.
```

### Scenario: Incomplete API Implementation
**When**: Controllers exist but have no methods or empty implementations
**Recovery**:
1. Note incomplete implementation
2. Generate skeleton documentation
3. Mark sections as "NOT IMPLEMENTED"
**User Message**:
```
⚠ API appears incomplete. Found 5 controllers but 3 have no implemented endpoints.

Generated documentation for:
- 12 complete endpoints ✓
- 5 skeleton endpoints (marked NOT IMPLEMENTED) ⚠

Recommendation: Re-run after API implementation is complete.
```

### Scenario: No XML Comments
**When**: Code lacks XML comments for descriptions
**Recovery**:
1. Generate documentation without descriptions
2. Note missing comments
3. Infer descriptions from method names where possible
**User Message**:
```
⚠ Many endpoints lack XML documentation comments.

Documentation generated:
- 41 endpoints documented ✓
- 28 with descriptions (from XML comments) ✓
- 13 without descriptions (inferred from method names) ⚠

Recommendation: Add XML comments for better documentation quality.
```

### Scenario: Confluence MCP Unavailable (--publish flag)
**When**: User requested publish but Confluence MCP not configured
**Recovery**:
1. Generate documentation locally
2. Provide instructions for manual upload
**User Message**:
```
⚠ Confluence MCP not available. Cannot auto-publish.

Documentation generated locally:
- File: output/documentation/api-docs-20260116-143022.md ✓

To publish manually:
1. Open Confluence space
2. Create new page
3. Copy content from generated file
4. Adjust formatting as needed

Or configure Confluence MCP for auto-publishing.
```
